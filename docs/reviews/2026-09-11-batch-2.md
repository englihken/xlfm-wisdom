**实现要点**（沿用 block-scoped 思路，没有重写）：

- 数字 token → **(主语, 数字) 对**。主语来自同一句里的 `《…》|大悲咒|心经|礼佛…|往生咒|解结咒…`；`张` 一律绑 小房子；句内找不到就回退到同一 block 里上一个提到的主语；再找不到就是裸数字，按旧规则（任一来源出现过即可）。
- 句子方向：整句按「数字→前主语」与「数字→后主语」两种绑法的**总字距**取小者，所以 `《大悲咒》7遍、《心经》7遍` 绑前，`三遍《大悲咒》，三遍《心经》` 绑后；块从括号中间切开（`大悲咒》，三遍《心经》…`）也不会错绑（第一版按「先出现者」判方向在这里错绑了，R10/R12 因此被 strip，已改）。
- 来源侧同样抽对；草稿对 (S,N) 落地条件：来源有 (S,N)，或来源有**裸** N。裸草稿数字：来源有 N 即可（现状）。
- 语气（句级，带块级引导）：`你念的|你说的|你提到…` → quote；`台长曾|对一位|那位同修|案例中|对类似情况` → narrate（引导句之后同块的列表行也算 narrate，除非该句自己写了「建议」）；`建议|可以念|每天念|要念|念N…` → advise；其余 plain。quote 优先于 advise。
- 访客数字：quote/plain/narrate 允许，advise → `number_visitor_as_advice`。
- `type='case_qa'` 来源（玄艺综述／玄艺问答）的数字：只在 narrate 语气允许，其余 → `number_case_generalized`——个案≠通则 从提示词降到护栏。`checkDraft` 新增 `caseTexts`，care-pipeline 与回归脚本都传。
- 组织审定 规则保持 token 级、只作用于 canonical 主题行，先于对检查。
- strip 按对删句（只删把 N 绑到该主语的句子）；裸违规仍删所有带 N 的句子。重试指令按原因分三种措辞，并写出主语（「礼佛 49遍」这一组合）。
- 中文数字 tokenization 保留（一遍至七遍、二十一遍…）。

**R1–R15 在 F01 之后**：第一版对绑定出错时 R10/R12/R13 被 strip（6 项失败）；修正方向判定后 83/86，剩 R14「缺《解结咒》」和 R13 两项措辞形态检查（护栏 clean，不是 F01 造成；见 §7 最终跑）。

## 3. F03 — 持久限流 + 输入上限（`src/lib/chat-rate-limit.ts`）

- 计数在 Supabase `rate_limits`（你建的表 + `rate_limit_hit(key, window_start)`，已验证：同键两次调用返回 1、2）。双 key：`bid:{browserId}` 与 `ip:{x-forwarded-for 首段}`；10 分钟窗口（`floor(now/10min)`）；上限 **20 条/浏览器、40 条/IP**（IP 松一些，NAT 共享）。
- 超限 → `429` + `{error:'rate_limited', message:<三语诚实的话>, retryAfterSec}` + `Retry-After`，**不做检索、不调模型**；两把 key 都先计数，所以被拦的请求也留在表里。页面对 429 显示服务端那句话（不是「系统有点问题」）。
- 限流器读不到（存储关/RPC 错）→ fail-open 放行并记日志——限流器坏了不能把聊天拖下水。
- 请求体运行时校验：`message` 非空且 ≤ 2,000 字；`conversation` ≤ 20 轮、每轮 `role` 只能 user/assistant、内容 ≤ 6,000 字；`language` ∈ zh/en/id（否则 zh）；`conversationId` 必须是 UUID；`browserId` ≤ 64 字。页面发送前把 volunteer 映射成 assistant，并只带最近 20 轮。
- 24 小时拦截数：见 §7（上线后查 `Σ max(0, count − limit)`）。
